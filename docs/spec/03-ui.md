# UI Design Specification

## Overview

The Work Management Platform follows a modern business application design style.

The interface should feel:

* Professional
* Clean
* Fast
* Organized
* Calm
* Information-focused

The UI should prioritize usability and clarity over visual decoration.

The visual identity should reflect the client's existing brand colors while remaining appropriate for a modern productivity and operations platform.

---

# Design Direction

The design language combines:

* Clean productivity software
* Modern SaaS dashboards
* Business information systems
* The client's established dark teal and muted gold brand identity

The interface should provide:

* Clear hierarchy
* Fast workflows
* Predictable interactions
* High information density
* Strong readability
* Subtle brand expression

Brand colors should be used intentionally rather than applying every brand color to every component.

The application should feel like a professional operational system first and a branded product second.

# Color Usage Principles

The interface should primarily use the dark teal family.

The recommended hierarchy is:

```text
Primary:
#002723

Primary Hover:
#02443A

Secondary:
#428177

Accent:
#B9A779

Accent Surface:
#EBE8D7

Text:
#161616

Muted Text:
#3C3C3D

Surface:
#FFFFFF
```

Do not use all brand colors at equal visual weight.

The dark teal should establish the primary identity.

The lighter teal should support interaction and secondary emphasis.

Gold should be used sparingly for:

* Important highlights
* Selected indicators
* Special emphasis
* Small decorative accents
* Important dashboard highlights

Gold should generally not be used for large blocks of text or large filled areas.

The warm beige should be used as a subtle surface color rather than the main page background.

---

# Color Tokens

The implementation should expose semantic design tokens rather than hard-coding brand colors throughout components.

Recommended semantic mapping:

```text
--primary: #002723
--primary-hover: #02443A
--secondary: #428177

--accent: #B9A779
--accent-muted: #958563
--accent-surface: #EBE8D7

--foreground: #161616
--muted-foreground: #3C3C3D

--background: #F8F8F5
--surface: #FFFFFF

--border: #E4E4DF
```

The exact generated Tailwind/shadcn color tokens may differ as long as the visual hierarchy remains consistent.

Avoid using raw hex values repeatedly inside components.

Prefer semantic Tailwind classes and CSS variables.

# RTL and Arabic First

Arabic is the primary interface language.

All screens must be designed RTL-first.

RTL requirements:

* Layout direction is right-to-left.
* Navigation starts from the right.
* Text alignment follows Arabic conventions.
* Icons should respect direction.
* Forms should flow naturally.
* Tables should remain readable.
* Dates and numbers should be formatted appropriately.

Do not simply mirror an English layout.

The UI should be designed naturally for Arabic users.

# Forms

Forms should follow consistent rules.

Requirements:

* Labels always visible.
* Validation messages below fields.
* Errors should be clear.
* Required fields indicated.
* Submit actions grouped together.
* Inputs must have clear focus states.

Forms should not use hidden labels.

Primary form actions should use the primary dark teal.

---

# Tables

Tables are a core part of the application.

Requirements:

* Sorting (single active column; click toggles ascending/descending)
* Filtering (server-side)
* Pagination with row options **25 / 50 / 100** (default 25)
* Search
* Visible row/result counts (e.g. “showing X–Y of Z”)
* Column visibility where useful

Tables should support:

* Loading states
* Empty states
* Error states

Tables should prioritize information density while maintaining readable spacing.

Use subtle borders and neutral surfaces rather than heavy card styling.

Shared UI helpers:

* `TablePagination`
* `SortableTableHead`

Do not load unlimited records into table pages.

# Success Feedback

Every successful user-submitted action must show clear success feedback.

Use a pattern that fits the screen:

* Inline alert / banner
* Snackbar / toast
* Inline form success message
* Explicit result inside a confirmation dialog

Do not treat a silent dialog close or a quiet list refresh as enough feedback.

Failure feedback is equally required and must be clear and translated.

---

# Empty States

Every list requires a useful empty state.

Example:

```text
لا توجد مشاريع حالياً

ابدأ بإنشاء مشروع جديد
```

Empty states should:

* Explain the situation.
* Suggest the next action.
* Avoid unnecessary decoration.

Primary empty-state actions should use the primary dark teal.

---

# Confirmation Dialogs

Required for destructive actions.

Example:

Deleting a department:

Show:

* What will be deleted.
* Related records affected.
* Whether action can be undone.

Permanent deletion must have a strong warning.

Where appropriate, explain cascade effects explicitly.

Example:

```text
سيؤدي حذف القسم إلى حذف أو إزالة البيانات المرتبطة به.
```

The exact consequences should always reflect the actual database behavior.

# Accessibility

The application should support:

* Keyboard navigation
* Clear focus states
* Proper labels
* Screen readers

Brand colors must meet appropriate contrast requirements.

In particular:

* Do not use `#428177` as small text on white unless contrast is sufficient.
* Do not use gold text for important information.
* Use dark teal or dark text for high-priority readable content.

Color must never be the only way to communicate status.

# Projects and Tasks UI (Milestone 3)

Routes:

* `/projects` — project list (table, filters, create)
* `/projects/[id]` — project detail with **tabs**: Tasks | Members
* `/projects/[id]/board` — Kanban (HTML5 drag-and-drop status updates)
* `/projects/[id]/gantt` — Gantt timeline (duration bars, dependency lines, overdue)

Kanban shows root tasks and subtasks as **separate cards**, each in the column matching its own status. Subtask cards show a parent hint; parent cards show subtask progress (`done/total`). Dragging updates only that card.

* `/tasks` — task list with advanced filters (status, priority, department, project, assignee, due range)
* `/tasks/[id]` — task detail tabs: Overview | Dependencies | Comments | Attachments | Activity
* `/departments/[id]` — department detail with **tabs**: Projects | Members

Kanban columns follow task statuses with semantic colors (Not Started gray, In Progress blue/teal, Blocked orange, Done green).

Gantt uses logical `inset-inline-start` positioning for RTL; overdue bars use destructive styling.

# Breadcrumbs

Detail and nested pages must show a breadcrumb trail above the page title.

Shared component: `Breadcrumbs`

Examples:

* الأقسام → المناهج
* المشاريع → المناهج → مشروع الموقع → لوحة كانبان
* المهام → مهمة التصميم

Intermediate items are links; the current page is plain text.

Do not rely only on a single “back to list” link on detail screens.

---

# Tabs on Detail Pages

When a detail page contains peer content regions (members, tasks, projects, history), present them as tabs — not stacked sections.

Shared components: `Tabs`, `TabPanel`

Tab actions (Add member, Create task) belong on the trailing side of the tab list for the active tab.

Do not put secondary content below a table on the same tab. If the table grows, that content becomes unreachable. Use another tab instead.

---

# Inline Editing in List Views

Users should update important project/task/subtask fields from list views without opening the detail screen.

Typical fields: title, status, assignee, priority, estimated hours (subtasks only), due/end dates.

Parent task hours are always the sum of subtask hours (0 with no subtasks) — never edited on the parent.

Task lists must show subtask counts, expand in-place, and support quick add (+), copy, and delete while staying on the list.

Every list row must still provide clear navigation to its detail page (title link and/or open action) for richer context later (activity, attachments, etc.).

Shared component for task rows: `TasksListTable`

Pages should compose existing components.

* One-off layouts

# Product Feel

Every screen should answer:

1. Where am I?
2. What information matters?
3. What action should I take?

The interface should feel like a professional operational tool.

The brand should be recognizable through:

* Deep teal structure
* Subtle lighter teal interaction
* Restrained gold accents
* Warm neutral surfaces
* Strong Arabic typography

The interface should never feel overly decorative or overly branded.

The primary goal remains clarity, speed, and effective work management.
