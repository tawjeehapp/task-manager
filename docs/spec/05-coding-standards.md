# Coding Standards

## Overview

This document defines the coding standards for the Work Management Platform.

The purpose is to ensure:

- Consistent code structure
- Maintainable features
- Clear separation of concerns
- Predictable patterns
- High-quality AI-assisted development

All code generated by developers or AI tools must follow these standards.

---

# General Principles

## Prefer Simplicity

Do not introduce complexity unless there is a clear requirement.

Avoid:

- Unnecessary abstractions
- Premature optimization
- Generic frameworks inside the application
- Complex state management

Prefer:

- Clear functions
- Small components
- Explicit behavior

---

## Separation of Concerns

Each layer has a responsibility.

```
UI

↓

Hooks / Queries

↓

API Routes

↓

Services

↓

Database
```

Do not mix responsibilities.

---

Example:

```
src/

app/

    projects/
    tasks/
    attendance/

features/

    projects/

        components/
        services/
        queries/
        mutations/
        schemas/
        types/
        utils/


components/

    ui/
    shared/


lib/

    supabase/
    auth/
    permissions/
    utils/


types/

hooks/

config/
```

---

# Feature Organization

Each major module owns its code.

Example:

```
features/tasks/

components/

    task-card.tsx
    task-table.tsx
    task-form.tsx


services/

    create-task.ts
    update-task.ts


queries/

    use-tasks.ts


mutations/

    use-create-task.ts


schemas/

    task.schema.ts


types/

    task.types.ts
```

---

# Components

## Component Rules

Components should:

- Be small
- Have one responsibility
- Be reusable when appropriate

Avoid:

- Large page components
- Business logic inside JSX
- Direct database access

---

## Component Types

### UI Components

Generic reusable components.

Example:

```
components/ui/button.tsx
```

Provided by shadcn/ui.

---

### Shared Components

Used across multiple features.

Example:

```
components/shared/data-table.tsx
```

---

### Feature Components

Specific to a module.

Example:

```
features/tasks/components/task-card.tsx
```

---

# Server Components

Default choice.

Use for:

- Pages
- Data display
- Layouts
- Static content

Avoid converting components to client components without a reason.

---

# Client Components

Use only when required.

Examples:

- Browser APIs
- Interactive state
- Drag and drop
- Complex forms

Every client component should have a clear reason.

---

# TypeScript Rules

Use TypeScript everywhere.

Avoid:

```
any
```

unless absolutely necessary.

Prefer:

```
unknown
```

with proper handling.

---

# Types

Types should live close to their feature.

Example:

```
features/tasks/types/task.types.ts
```

Global types only for truly shared concepts.

---

# Naming Conventions

## Files

Use kebab-case.

Examples:

```
task-card.tsx

create-project.ts

use-tasks.ts
```

---

## Components

Use PascalCase.

Example:

```
TaskCard
ProjectTable
```

---

## Functions

Use camelCase.

Examples:

```
createTask()

getProjects()
```

---

## Database

Use snake_case.

Examples:

```
created_at

project_members
```

---

# Hooks

Custom hooks must start with:

```
use
```

Examples:

```
useTasks()

useCreateProject()
```

Hooks should not contain large business logic.

---

# Forms

All forms should use:

- React Hook Form
- Zod validation

Pattern:

```
schema

↓

form

↓

mutation

↓

API
```

---

# API Calls

Never call APIs directly inside components.

Use:

- Query hooks
- Mutation hooks

Example:

```
useProjects()

useCreateProject()
```

---

# Supabase Usage

Supabase access must happen through:

```
lib/supabase

or

feature services
```

Never:

```
component

↓

supabase
```

---

# Error Handling

All errors must be handled.

User-facing errors should be:

- Clear
- Translated
- Actionable

Never show raw errors.

---

# Loading States

Every async operation requires:

- Loading state
- Error state
- Success feedback

Examples:

- Buttons
- Tables
- Pages

---

# Success Feedback

Every successful user-submitted action must provide visible success feedback.

Required for mutations such as:

- Create
- Update
- Delete
- Activate / deactivate
- Password reset
- Approvals and similar workflows

Acceptable patterns:

- Page alert / banner
- Snackbar / toast
- Inline form success message
- Explicit confirmation in a dialog result

Not acceptable:

- Dialog closes with no message
- List refreshes with no indication of what succeeded
- Silent success

Success and error messages must be:

- Clear
- Translated
- Shown close to the user’s action context when practical

---

# Empty States

Every collection view requires an empty state.

Examples:

- No projects
- No tasks
- No notifications

---

# Database Changes

Database changes must:

- Have migrations
- Be reviewed
- Update documentation

Never manually modify production databases.

---

# Environment Variables

Environment variables must be:

- Documented
- Validated
- Never committed

Example:

```
.env.example
```

---

# Imports

Prefer absolute imports.

Example:

Good:

```
@/features/tasks
```

Avoid:

```
../../../features/tasks
```

---

# Comments

Comments should explain:

- Why something exists

Avoid comments explaining obvious code.

Bad:

```
// increment counter
counter++
```

Good:

```
// Prevent duplicate notifications during retries
```

---

# Logging

Use structured logging.

Avoid:

```
console.log()
```

in production code.

---

# Security

Never trust client input.

Always validate:

- API input
- Permissions
- Ownership

---

# Performance

Consider performance for:

- Large tables
- Reports
- Dashboards

Use:

- Pagination with page sizes **25 / 50 / 100** (default 25)
- Single-column sorting
- Server-side filtering
- Proper indexes

Shared table UI:

- `components/shared/table-pagination.tsx`
- `components/shared/sortable-table-head.tsx`
- `lib/table/constants.ts`

List API responses should include `items`, `total`, `page`, `pageSize`, and `totalPages`.

---

# Testing Strategy

Initial testing focuses on:

## Critical Business Logic

Examples:

- Permission checks
- Approval workflows
- Leave calculations
- Task dependency rules

---

# Git Standards

Commits should be clear.

Examples:

```
feat: add task assignment

fix: correct attendance calculation

docs: update database specification
```

---

# AI Development Rules

When using AI coding tools:

- Always read existing documentation first.
- Do not create new patterns without approval.
- Follow existing folder structure.
- Avoid introducing new libraries without justification.
- Prefer consistency over novelty.
